# 竹南冷凍公司－倉儲管理系統 2.0 技術方案

## 1. 方案摘要

本系統先以瀏覽器可使用的 Web 應用實作，採用前後端分層的單體架構。技術選型以容易開發、展示與維護為優先，並將庫存異動的正確性放在 UI 效果之前。

| 層次 | 建議技術 | 用途 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 倉庫總覽、進出貨、盤點、報廢與異動紀錄頁面 |
| 後端 | Node.js、TypeScript、Fastify | API、輸入驗證及庫存業務規則 |
| 資料庫 | PostgreSQL | 保存主檔、庫存批次及不可遺漏的異動紀錄 |
| 資料存取 | Prisma ORM 與資料庫 Migration | 型別安全的資料存取及可追蹤的結構更新 |
| 驗證 | Vitest；API 層可搭配 Supertest | 驗證 FIFO、不可負庫存及交易流程 |

第一版維持一個後端服務與一個資料庫，不引入微服務、訊息佇列或複雜雲端架構。

## 2. 為什麼先做 Web，而不是 Electron

目前需求是單一倉儲管理人員透過畫面操作系統，沒有離線操作、桌面硬體整合或必須安裝程式的要求。因此 Web 版較適合本次 Demo：開啟瀏覽器即可操作，更新與展示也較簡單。

Electron 可以把 Web 前端包裝成桌面程式，但會增加安裝檔、版本更新與桌面端維護工作。若後續確認需要離線使用或本機設備整合，再評估 Electron；庫存規則仍應由共用的後端 API 與資料庫處理，避免把交易邏輯只放在桌面客戶端。

## 3. 系統架構

```text
瀏覽器（React）
       │ HTTPS / JSON API
       ▼
Node.js API（驗證、權限、庫存交易）
       │ 資料庫交易
       ▼
PostgreSQL
```

前端負責表單、查詢與清楚呈現操作結果；後端是庫存規則的唯一執行位置；PostgreSQL 保存正式資料。所有新增、出貨及報廢操作由後端以資料庫交易完成，不能只在畫面上加減數量。

## 4. 核心資料概念

建議將庫存以「批次」為單位保存。每筆批次庫存至少關聯倉庫、商品、儲位、數量及進貨時間；批次還可記錄有效期限。倉庫、商品與儲位作為主檔管理。

主要資料概念如下：

- **Warehouse、Product、Location**：倉庫、商品及儲位主檔。
- **InventoryBatch**：批次庫存，包含倉庫、商品、儲位、進貨時間、數量與批次資訊。
- **InventoryTransaction**：統一的庫存異動明細，記錄異動類型、數量、原因、時間及操作人員；進貨、出貨、報廢與盤點調整都要留下記錄。
- **Stocktake / StocktakeLine**：盤點單及盤點明細，保存系統數量、實際數量、差異與盤點時間。這能補足原計畫只提到盤點、未明確保存盤點差異的部分。

庫存數量應使用整數（本 Demo 的單位為箱）。只有在未來確定會管理重量或小數單位時，再調整為適合的精度。資料表應設定外鍵、必要欄位及數量檢查條件；歷史異動以新增記錄為主，不直接改寫或刪除。

## 5. 重要交易規則

### 進貨

後端驗證倉庫、商品、正整數數量與非空儲位，在同一個資料庫交易中建立批次庫存及進貨異動記錄。進貨時間由伺服器／資料庫產生，不接受前端任意指定作為實際進貨時間。

### FIFO 出貨

依指定倉庫與商品找出仍有庫存的批次，依 `received_at` 由早到晚排序。若同一時間有多個批次，以穩定的次要排序欄位（例如批次 ID）決定順序。一次出貨可能跨越多個批次，因此應逐批扣減並記錄每個批次實際扣除數量與儲位。

出貨前先確認總可用庫存足夠，再於交易中鎖定要扣減的批次並更新數量、建立出貨及異動記錄。若庫存不足，整筆交易回滾並回覆可用數量，不能留下部分扣庫存的結果。

### 報廢與盤點

報廢需指定批次、正整數數量及原因，在交易中檢查數量不超過該批次可用庫存，扣減庫存並建立報廢異動。

盤點先保存盤點當下各批次的系統數量與實際數量。盤點確認時，若差異需要調整庫存，建立具原因的盤點調整異動；不可直接覆寫歷史交易。腐爛品可由盤點發現後另行登記報廢，保留明確的報廢原因與批次關聯。

## 6. API 與主要畫面範圍

初版 API 可按業務資源切分，例如：

- `GET /api/inventory`：依倉庫、商品查詢批次庫存與總量。
- `POST /api/inbounds`：建立進貨。
- `POST /api/outbounds`：建立出貨並由後端套用 FIFO。
- `POST /api/stocktakes`、`POST /api/stocktakes/:id/confirm`：建立與確認盤點。
- `POST /api/scraps`：建立報廢。
- `GET /api/transactions`：查詢庫存異動紀錄。
- 倉庫、商品與儲位的基本查詢及維護 API。

畫面先涵蓋 Dashboard、庫存總覽、進貨、出貨、盤點、報廢、異動紀錄與基本資料。出貨確認前顯示預計 FIFO 取貨批次與儲位；真正確認時仍由後端重新驗證及計算，避免預覽後庫存改變造成錯誤。

## 7. 部署與資料安全

Demo 可先在一台電腦或區域網路主機啟動 Web 前端、API 與 PostgreSQL，讓展示設備透過瀏覽器連線。資料庫連線資訊使用環境變數保存，不寫入前端程式或版本庫。提供資料庫 Migration 與可重複執行的 Demo 種子資料，種子資料包含兩個倉庫、商品及可驗證 FIFO 的不同進貨批次。

若系統供多台設備或正式營運使用，應部署在固定主機或雲端服務，啟用 HTTPS、帳號登入、權限、定期備份及還原程序。第一版若 Demo 只有一位操作人員，可以先採簡單登入或受限的內網環境；是否需要完整帳號與角色管理，應在正式上線前確認。

## 8. 實作順序

1. 建立資料庫結構、Migration 與 Demo 種子資料。
2. 完成倉庫、商品、儲位及批次庫存查詢。
3. 完成進貨交易與異動紀錄。
4. 完成 FIFO 出貨、批次鎖定及庫存不足處理。
5. 完成盤點、差異調整與報廢。
6. 建立 Demo 所需頁面、操作提示及交易結果回饋。
7. 依驗收劇本驗證完整流程及重新查詢後的最終庫存。

## 9. 驗收重點

- 兩個倉庫及各自儲位的庫存可分開查詢。
- 進貨建立新批次，時間由系統記錄，儲位不可空白。
- 出貨固定按最早進貨批次扣庫存；多批次出貨時能正確拆分。
- 庫存不足或報廢數量超過庫存時，操作失敗且資料完全不變。
- 進貨、出貨、報廢和盤點調整都有對應異動記錄。
- 盤點保存系統量、實際量及差異。
- 完成計畫書的 Demo 流程後，重新查詢所得庫存與每筆交易一致。

## 10. 尚待確認的營運決策

技術架構可先依本方案開始；正式使用前仍需確認登入與操作人員紀錄需求、倉庫是否會同時多人操作、是否需要離線、單位是否可能包含重量或小數，以及部署主機與備份責任。這些決定可能影響權限、併發控制與部署方式，但不妨礙先完成單一操作人員的 Demo。
